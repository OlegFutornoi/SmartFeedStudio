# 📦 Скіл `git-commit`: Кероване вивантаження та релізний конвеєр

> **Шлях:** [`.agents/skills/git-commit/README.md`](./README.md)  
> **Основна інструкція:** [`SKILL.md`](./SKILL.md)  
> **Призначення:** Забезпечення чистого, контрольованого вивантаження коду в Git та запобігання автоматичному створенню нових версій додатку на кожен щоденний коміт.

---

## 📌 1. Чому виникала проблема автоматичних релізів

У ранніх версіях регламенту на кожен виклик `/git-commit` безумовно виконувалися команди:

```bash
git tag -a vX.Y.Z -m "Release vX.Y.Z: ..."
git push origin <branch> --tags
```

Оскільки в репозиторії налаштовано GitHub Actions:

- [`.github/workflows/release.yml`](../../../.github/workflows/release.yml) — тригериться на `push: tags: ['v*']` і запускає повну збірку Desktop додатків на трьох ОС (Ubuntu, macOS, Windows) та створює новий GitHub Release.
- [`.github/workflows/docker.yml`](../../../.github/workflows/docker.yml) — тригериться на `push: tags: ['v*']` і білдить/пушить Docker-образи бекенду та адмін-порталу.

**В результаті будь-який рутинний коміт створював нову версію додатку та спалював хвилини CI-раннерів.**

## 🎛️ 2. Два режими роботи `git-commit`

Тепер скіл чітко розділяє звичайну фіксацію коду від офіційного релізу:

| Виклик команди                         | Режим                 | Створює Git-тег `v*`? | Тригерить Release Action? | Що робить                                                                                                       |
| :------------------------------------- | :-------------------- | :-------------------: | :-----------------------: | :-------------------------------------------------------------------------------------------------------------- |
| **`/git-commit`** або **`/commit`**    | **Regular (Default)** |       ❌ **Ні**       |         ❌ **Ні**         | `verify:build` → Conventional Commit → `git push origin <branch>` **без тегів**. Жодного релізу не створюється. |
| **`/git-commit --skip-ci`**            | **Regular (Skip CI)** |       ❌ **Ні**       |         ❌ **Ні**         | Додає `[skip ci]` до повідомлення коміту, повністю пропускаючи виконання будь-яких GitHub Actions.              |
| **`/git-commit --release`** (або `-r`) | **Release (Patch)**   |      ✅ **Так**       |        ✅ **Так**         | Піднімає patch (`+0.0.1`), синхронізує конфіги, створює тег `v*` та пушить його для збірки бінарників.          |
| **`/git-commit --release minor`**      | **Release (Minor)**   |      ✅ **Так**       |        ✅ **Так**         | Піднімає minor (`+0.1.0`), синхронізує конфіги, створює тег `v*` та пушить його для збірки бінарників.          |
| **`/git-commit --release major`**      | **Release (Major)**   |      ✅ **Так**       |        ✅ **Так**         | Піднімає major (`+1.0.0`), синхронізує конфіги, створює тег `v*` та пушить його для збірки бінарників.          |
| **`/git-commit --version 1.20.0`**     | **Release (Exact)**   |      ✅ **Так**       |        ✅ **Так**         | Встановлює точну версію, синхронізує конфіги, створює тег `v*` та пушить його для збірки бінарників.            |

## 🚀 3. Детальні пайплайни виконання

### 🅰️ Звичайний режим (Regular Mode — вивантаження без екшенів)

Викликається за замовчуванням за командами: `/git-commit`, `/commit`, _«закоміть»_, _«вивантаж»_, _«зроби коміт»_.

1. **Pre-Commit Integrity Gate**:

   ```bash
   pnpm verify:build
   ```

   Перевіряє контракти `@smartfeed/shared`, генерацію Prisma, статичну типізацію `tsc --noEmit` у всіх пакетах, збірки NestJS/Vite та перевірку Rust Tauri.

2. **Стейджинг файлів**:

   ```bash
   git add .
   ```

   _(Перевіряється відсутність секретів `.env` у списку змін)._

3. **Створення Conventional Commit**:

   ```bash
   git commit -m "<type>(<scope>): <опис змін>"
   ```

4. **Чистий Push гілки**:
   ```bash
   git push origin <current-branch>
   ```
   > 🛑 **Важливо:** Команда `git tag` НЕ викликається, прапорець `--tags` НЕ передається. Код з'являється на GitHub, але жодних релізних workflow не запускається.

---

### 🅱️ Релізний режим (Release Mode — створення нової версії)

Викликається ТІЛЬКИ за наявності параметра `--release` або явного текстового запиту користувача (_«випусти реліз»_, _«створи нову версію»_).

1. **Pre-Commit Integrity Gate**:

   ```bash
   pnpm verify:build
   ```

2. **Розрахунок версії та синхронізація файлів**:

   ```bash
   node scripts/bump-version.mjs [patch|minor|major|<version>]
   ```

   Скрипт автоматично синхронізує версію в:
   - `apps/desktop/src-tauri/tauri.conf.json` (`version`)
   - `apps/desktop/src-tauri/Cargo.toml` (`version = "..."`)
   - `apps/desktop/package.json` (`version`)
   - `package.json` (кореневий файл)

3. **Стейджинг оновлених конфігурацій**:

   ```bash
   git add .
   ```

4. **Релізний коміт**:

   ```bash
   git commit -m "chore(release): bump version to vX.Y.Z"
   ```

5. **Створення анотованого тегу**:

   ```bash
   git tag -a vX.Y.Z -m "Release vX.Y.Z: <Короткий опис релізу>"
   ```

6. **Пуш гілки та тегу**:
   ```bash
   git push origin <current-branch> && git push origin vX.Y.Z
   ```
   > 🚀 Тільки на цьому кроці пуш тегу `v*` активує GitHub Action `Release Desktop App` та `Publish Docker Images`.

У кореневому [`package.json`](../../../package.json) налаштовані швидкі команди:

## 🛡️ 5. Правила безпеки Git (Git Safety Protocol)

1. **Жодних автономних комітів**: Агент **НІКОЛИ** не робить `git commit` чи `git push` самостійно без явної команди користувача.
2. **Заборона тегів у звичайному режимі**: Створення та відправка тегів заблоковані для звичайних комітів.
3. **Заборона деструктивних команд**: Заборонено використовувати `--force`, `reset --hard` чи модифікувати глобальний `git config`.
4. **Zero-Broken-Build**: Заборонено комітити або пушити код, якщо `pnpm verify:build` повертає помилку.
