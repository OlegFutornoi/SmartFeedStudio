# 💬 SmartFeed Studio — Communication, Token Economy & Engineering Research Rules

## 📌 1. Жорсткий регламент відповідей у чаті та економія токенів (Zero Plan Dumping)

Щоб уникнути марного спалювання токенів та дублювання інформації:

1. **Короткі та прямі відповіді в чаті (Strict Chat Brevity)**:
   - Відповіді в чаті **ЗОБОВ'ЯЗАНІ бути лаконічними, структурованими та по суті**.
   - Заборонено генерувати довгі есеї, пояснювальні «простирадла» тексту чи повторювати одне й те саме різними словами.
2. **Весь детальний контент — виключно у файли планування (Zero Plan Dumping)**:
   - Повний детальний план, архітектура, декомпозиція задач, списки файлів, DTO, схеми та кроки реалізації **ЗАПИСУЮТЬСЯ ВИКЛЮЧНО у файл плану `plans/active/<feature>.md`** (або у відповідний артефакт/документ).
   - **СУВОРА ЗАБОРОНА ДУБЛЮВАННЯ**: Категорично заборонено одночасно записувати план у файл і копіювати цей же повний план (чи його великі секції) у повідомлення чату.
   - **Формат повідомлення в чаті**:
     - 1–2 речення підсумку: що зроблено / що заплановано.
     - Клікабельне посилання на документ плану: `[План реалізації](file:///Users/oleg/AQA/SmartFeedStudio/plans/active/<feature>.md)`.
     - Якщо потрібне підтвердження — одне пряме запитання до користувача.

## 💎 2. Інженерна якість понад "аби працювало" (Reliability & Quality > "Working is Enough")

Для всіх агентів (`agents_frontend`, `agents_backend`, `agents_review`, `agents_qa`, `agents_devops`) діє залізне правило:

1. **"Працює" — це не критерій прийнятності**:
   - Заборонено писати код за принципом «швидко зліпити, аби пройшов перший клік або один тест».
   - Будь-який швидкий «костиль», заглушка, мовчазний `catch {}`, приведення до `any`, пропущений індекс чи захардкоджений колір вважається інженерним браком.
2. **Глибокий аналіз та вибір найкращого рішення**:
   - Перед написанням коду агент зобов'язаний проаналізувати варіанти реалізації та вибрати спосіб **максимально ефективний, продуктивний, масштабований і надійний**.
   - Рішення має враховувати граничні випадки, роботу з великими обсягами даних, паралельні операції, очищення ресурсів, типобезпеку та каскадну цілісність.

## 🔍 3. Обов'язкове оновлення інформації через `context7` та MCP (Upfront Research)

Перед проектуванням архітектури, зміною конфігурацій чи написанням коду для будь-яких бібліотек/фреймворків:

1. **Не кодити за застарілою пам'яттю (Zero Guesswork & Hallucination)**:
   - Тренувальні дані моделей застарівають, API змінюються, з'являються нові рекомендовані практики (Next.js 14 App Router, Tauri v2, React 18/19, Prisma, BullMQ, Tailwind v4 тощо).
2. **Обов'язковий пошук через `context7` MCP**:
   - При роботі з будь-якою зовнішньою бібліотекою чи SDK викликати `context7` MCP (`call_mcp_tool` з `ServerName: "context7"`):
     - `resolve-library-id` — отримати актуальний ідентифікатор бібліотеки.
     - `query-docs` — отримати свіжі офіційні сигнатури, приклади використання та рекомендації авторів.
3. **Профільні MCP проекту за призначенням**:
   - **`postgres`** — перевірка реальних планів запитів (`EXPLAIN ANALYZE`), індексів та системних каталогів.
   - **`shadcn`** — перевірка офіційних компонентів, варіантів та токенів дизайн-системи.
   - **`firecrawl`** — актуальні веб-стандарти, специфікації маркетплейсів чи сторонніх XML/CSV фідів.
   - **`sentry`** — перевірка реальних стек-трейсів помилок перед фіксом.
