# Negative API Testing Patterns (Fintech & Insurance)

Цей посібник містить структуровані шаблони та кейси негативного тестування для API сервісів репозиторію (`CRM`, `IBPM`, `EWA`, `AIWA`, `OTP`, `Payment`).

---

## 1. Валідація схеми та вхідних даних (Schema & Payload Validation)

### 1.1. Обов'язкові поля верхнього рівня

При відсутності обов'язкових об'єктів або ключів:

- Пропущено `tariff`: очікується `400 Bad Request` із зазначенням відсутності інформації про тариф.
- Пропущено `vehicle`: очікується `400 Bad Request`.
- Пропущено `customer`: очікується `400 Bad Request`.

### 1.2. Персональні дані клієнта (`Customer`)

- **ІПН (taxId):**
  - Менше або більше 10 цифр (`12345`, `12345678901`).
  - Нечислові символи (`123456789A`).
  - Невалідна контрольна сума або дата народження з майбутнього.
- **Номер телефону:**
  - Некоректний формат (`12345`, `+1234567890`).
  - Неіснуючий код оператора в Україні.
- **ПІБ:**
  - Порожні рядки (`firstName: ""`).
  - Недопустимі спецсимволи (`<script>`, SQL-ін'єкції).
- **Документи:**
  - Дата видачі паспорта пізніше поточної дати (дата з майбутнього).
  - Дата закінчення терміну дії раніше дати видачі.
  - Порожній номер/серія документа.
  - Невідповідність типу документа (`type: "passport"` з полями `idCardNumber`).

## 2. Бізнес-правила та межі (Business Boundaries)

### 2.1. Вік водія (`driversAgeMin`)

- Водій молодше 18 років (`driversAgeMin: 16`) для категорій авто B/C.
- Несумісність року народження з мінімальним віком водія.

### 2.2. Пільгові категорії (`Privilege`)

- Спроба отримати пільговий тариф без відповідного документа (напр., `privilege: "pensioner"`, але передано звичайний паспорт замість пенсійного посвідчення).
- Спроба оформити пільгу на юрособу або на авто, об'єм двигуна якого перевищує встановлені законодавством норми (більше 2500 см³ для ОСЦПВ).

### 2.3. Тарифи та франшизи

- Передача неіснуючого `tariffId` (`999999999`).
- Передача застарілого/простроченого кеш-ключа тарифу.
- Невідповідність `bankSlug` або кількості платежів `installmentParts` для даного партнера.

---

## 3. Стан машини переходів (State Machine & Concurrency)

### 3.1. OTP верифікація

- Підтвердження ліда невірним кодом (`000000` або `abc`).
- Підтвердження вже підтвердженого ліда (ідемпотентність або помилка).
- Спроба підтвердження після вичерпання ліміту спроб (Brute-force protection -> `429 Too Many Requests` або `400 Max attempts exceeded`).
- Спроба підтвердження простроченого OTP (понад 5-15 хвилин).

### 3.2. Оплата та Postback

- Спроба відправити payment postback на лід у статусі до OTP (`state === "draft"` або `state === "otp_pending"`).
- Невірна сума оплати у postback (`amount` менше за `appliedPayment` — недоплата).
- Невалідний `postbackUuid` або неіснуючий платіжний ідентифікатор.
- Повторний postback на вже успішно оплачений лід (`emitted`).

### 3.3. Дублікати та паралельні запити

- Одночасне відправлення двох однакових `submit` запитів для одного й того ж `leadId`.
- Спроба модифікувати лід після того, як договір перейшов у стан `emitted`.
